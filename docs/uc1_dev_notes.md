# UC1 — Developer notes

Design rationale that used to sit in comments and docstrings in the connector and playbook
code. The code keeps one-line "what / why not to change" comments; the reasoning is here,
organised by block (function) name. For architecture, flow and setup see
`uc1_implementation_plan.md`.

The original notes file the code pointed to was not part of this package. This one is rebuilt
from the comments that referenced it, the block notes in the playbook JSON and the plan doc, so
it holds what the code itself recorded, nothing more. Gaps are listed under
[Open items](#open-items).

## Keep in sync and leave alone

- **`.py` and JSON `userCode` must match.** Each playbook's custom-code regions exist twice: in
  the `.py` and in the JSON `coa.data.nodes.*.userCode`. Edit both, or the package imports
  with code that differs from what was reviewed (the bug fixed in `6d7901f`).
- **VPE scaffolding stays.** The `Custom Code Start/End` banners, the `phantom.debug("x() called")`
  lines and the long `action=None, success=None, ...` signatures on every block are generated by
  the SOAR visual playbook editor. Removing them gains nothing; the editor puts them back.
- **Connector changes need a version bump** (`app_version`); SOAR refuses an install that isn't
  strictly higher. See `RELEASING.md`.

## Why these blocks are custom code

SOAR's native blocks (action, utility/custom function, format, decision) don't cover these cases.

| Playbook | Block | Why code |
|---|---|---|
| `cyberark_credential_rotation` | `get_secret_from_vault` | Plain native `get secret` action; the parameters are built in a custom-code region so `address` is only sent when set. |
| | `build_config_update` | Parses the `get secret` action result and detects APPAP282E (password change in progress). No custom function wraps this. Saves `config_json`, `target_asset`, `error`, `password_change_in_process` via `save_run_data`. |
| | `run_test_connectivity` | Uses a synchronous REST `action_run` + poll, not `phantom.act("test connectivity")` + callback. It runs inside the callback chain of the `update_target_asset` custom function, where an async `act` would race with `on_finish`. Saves its result to `run_test_connectivity:output`. |
| | `format_error` | Conditional error classification: two-level `run_data` fallback (`build_config_update:error`, then `rotation_error`), APPAP282E substring match, `pending_recheck` vs `failed`. Format blocks only do `{0}`/`{1}` templating. Saves to `format_error:output`. |
| `cyberark_recheck_handler` | `check_recheck_artifact` | Iterates container artifacts by ID to find the newest "Recheck Request" and applies the bounded-retry guard (`MAX_RECHECK_ATTEMPTS = 3`) in one step. No native block does both. |
| | `dispatch_recheck` | Its inputs come from `run_data` (`check_recheck_artifact:target`). A native playbook block would need a standard datapath, not a JSON blob. |
| | `process_recheck_result` | Multi-mutation callback: REST child read, state-list upsert, note, optional retry artifact, severity re-evaluation. Everything is a synchronous platform API (no `phantom.act` / `custom_function`). |
| `cyberark_rotation_orchestrator` | `read_discover_result` | Bridge block. Reads `total_count` from the `discover_targets` custom function result; needed because the VPE misrenders a utility block that edges straight into a decision. |
| | `dispatch_rotations` | The VPE has no for-each primitive, so N targets are fanned out with async `phantom.playbook()`. Passes `target_asset`, `safe`, `username`, `pwd_field`, `user_field`, `address` to each child and saves `targets_info` to `run_data` for `collect_results`. |
| | `collect_results` | Callback from each child. See [Guards](#guards-and-idempotency). |
| | `build_summary` | Inline code, not a custom function: `phantom.custom_function()` would async-race with `on_finish`. Severity: all success → low, any failed → high, any pending → medium. |
| | `add_summary_note` | Synchronous `add_note`. |
| | `update_rotation_state` | Inline code: `phantom.get_list` / `set_list` are synchronous platform APIs, safe in a callback chain. |
| | `update_severity` | `phantom.set_severity` is synchronous and has no native block. A `phantom.custom_function(community/container_update)` here would async-race with `on_finish`. |

Rule behind most of these: **inside a callback chain, use synchronous platform APIs**. Anything
asynchronous (`phantom.act`, `phantom.custom_function`) can still be running when `on_finish` fires.

## Guards and idempotency

- **Orchestrator `on_start`:** runs once per container. It skips a container that carries a
  "Recheck Request" artifact; the recheck handler has the mirror-image guard (skips when there is
  none). The playbook trigger `artifact_created` fires on container *and* artifact creation, so
  these guards are what route each event to the right playbook.
- **`collect_results`:** callbacks run sequentially in SOAR, but all of them may see
  `completed == total`, because the REST query reflects the final state for every child. A
  `dispatch:summary_done` flag guards against duplicates. The count is REST-based, paginated
  (`MAX_PAGES = 20`, about 1000 rows, far beyond any realistic container) and idempotent.
- **`add_summary_note`:** repeats the guard as defense in depth, since `collect_results`'
  guard isn't atomic.
- **Recheck dispatch is REST-checked, not `run_data`-checked** (`_recheck_already_dispatched`),
  because `run_data` isn't shared across separate automation-triggered executions.
- **Recheck dispatch names** are per target and per attempt (`recheck_<asset>_<attempt>`,
  sanitised because asset names flow into a `playbook_run` name). History: every recheck used to
  be dispatched under the fixed name `recheck_rotation`, which made both the artifact-claim check
  and the child-result lookup unable to tell two targets' concurrent rechecks apart.
- **Candidate order:** the recheck handler takes the highest artifact id first and skips anything
  already dispatched.

## State list

Column order, in `update_rotation_state`, the recheck handler's upsert and
`custom_lists/cyberark_ccp_rotation_state.json`:

`asset, safe, user_field, pwd_field, address, connector, username, status, message, last_rotated, event_link`

Columns 1–5 are the vault mapping (operator-maintained), 6–11 are written by the playbooks.
The recheck handler's upsert must keep this order; the status column is index 7.

## Custom functions

- **`phantom.requests` carries the SOAR session's auth.** Don't replace it with the system
  `requests`. REST calls use `verify=False`.
- **`asset_update_configuration`:** looks the asset up by name first, since callers always pass
  names; a bare numeric string is only a fallback. It reads the current config and merges, then
  posts the whole config back with tags, name and description.
- **`asset_get_tagged_for_rotation`:** `configuration or {}` is deliberate, since an asset can
  have `configuration: null` present rather than absent. It returns a single `total_count = 0`
  sentinel instead of an empty list, because an empty list marks the custom function as failed
  on SOAR. The orchestrator's `build_summary` then treats a discovery error as high severity: a
  zero-target discovery is a real failure, not a quiet no-op.

## Open items

Found while moving this material out of the code. None changes behaviour today; they're here so
they aren't lost.

1. **Password-type fields on `asset_update_configuration`.** The original comment flags a risk
   around password-type fields on the write-back path, "a known open item, not yet fixed". The
   details were not preserved. Related context is in the plan doc: a `client_key` corruption on
   the CCP asset that recurred with no known cause. Nothing here establishes a link.
2. **Stale operator text in `format_no_targets_note`** (orchestrator `.py` and the JSON node 11
   template). It tells operators to set each asset's Description to
   `cyberark_ccp:safe=...`. Discovery has been driven by the `cyberark_ccp_rotation_state`
   custom list since the 2026-08-03 change described in the plan doc, so the text should point
   operators at that list and its columns instead.
3. **The `soar6` asset is undocumented** in `HANDOVER.md` (see the table above). A target SOAR
   needs an asset with that exact name, or the two blocks must be edited.
